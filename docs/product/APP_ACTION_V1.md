# Application et annulation Calendar — service v1

Issue41, Astra. `ActionService(connections, live, configuration=None, oauth_factory=GoogleOAuth, writer_factory=GoogleCalendarWriter)` ; aucun changement HTTP dans ce lot. Import direct `apps.api.actions.ActionService, ActionError`. ActionError expose `code`, `status`, message fixe.

Méthodes : `describe(session)`, `begin(session,{})`, `handles_callback(session,params)`, `callback(session,params)`, `forget(session,{})`, `execute(session,{revision,plan_id,approved:true})`, `undo(session,{receipt_id,approved:true})`, `discard(session)`. Begin retourne `{authorization_url,...}` du port OAuth. Les autres actions publiques retournent l’état décrit ci-dessous ; callback renseigne aussi `session.oauth_result` avec provider `google_calendar_write`. `handles_callback` compare uniquement le state opaque actif ; aucun réseau.

État public : `{provider:"google_calendar_write",configuration:"ready"|"missing"|"invalid",connected:bool,pending:bool,busy:bool,receipts:[{id,status,reason_codes,actions:[{event_id,before:{planned_start,planned_end},after:{planned_start,planned_end}|null}]}],budget:{executions,limit:10,remaining},audit:"memory_session_only"}`. Aucun token, ETag, hash ou données fournisseur. Execute/undo retournent cet état avec le reçu actualisé dans receipts. Codes ActionError : invalid_request400, actions_unavailable503, not_connected409, action_busy409, stale_plan409, invalid_plan400, budget_exhausted429, unknown_receipt404, action_failed502, session_expired401, operation_cancelled409.

Un OAuth distinct `google_calendar_write` exige exactement le scope calendar.events et conserve les flux PKCE/state et isolation existants. PROVIDERS readonly inchangé. Begin/forget explicites ; access_token seulement execute/undo. Configuration fournie par root, jamais lue depuis environnement. OAuth est instancié seulement si client/redirect valides et origine exacte.

Le service extrait les plans de `session.live_state.planning.plans` et les snapshots de `session.sources.google_calendar.canonical_data.events`, sous verrou. Il exige une révision identique, 1..5 opérations et des blocs personnels standalone sur primary, propriété et absence complète de participants. Seuls ces IDs deviennent flexibles. Permission niveau2 et hash calculés serveur. Clé idempotente dérivée session/révision/plan ; même requête après invalidation retrouve le reçu. Échecs après possible mutation restent unknown, jamais relancés automatiquement. Maximum10 tentatives d’exécution validées/session, budget et reçus conservés après oubli ; undo ne consomme pas ce compteur.

AuditStore(':memory:') par session : aucune durabilité ni restauration après fermeture/expiration promise. Les reçus restent sélectionnables après relecture d’agenda. Undo exige confirmation et reçu de cette session ; PlanExecutor et le writer refont préflight/ETag. Une opération à la fois, coordination avec live_busy et toutes les lectures de sources (Calendar et Gmail). Aucun I/O sous session.lock. La génération de consentement et l’identité live sont revalidées après refresh et avant les appels du writer et via `before_mutation` après son GET interne, immédiatement avant PATCH. Les writer_factory injectées acceptent ce callable optionnel et doivent l’invoquer au même endroit. Discard invalide immédiatement l’autorisation logique et les résultats live/intelligence ; il ne peut pas annuler un PATCH déjà parti. Une telle réponse reste auditée et ne recrée pas le live.

Hooks root obligatoires : discard après oubli/reconnexion Calendar et expiration ; root branche callback avant readonly callback si handles_callback vrai. HTTP exige session/Origin/CSRF pour actions ; aucune permission à partir d’un plan navigateur. Tests injectés couvrent PlanExecutor/AuditStore ; aucun compte ou écriture réelle.
